# `:task` Steps Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a `:do` step call another task — `{:task fmt}` or `{:task [deploy :arg/env "fast"]}` — so a task can run other tasks between its own steps.

**Tech Stack:** let-go (`.lg`), shapelet schemas (`rite.config`), `lgx test` for unit tests, `tests/e2e.sh` against the built `bin/rite`.

---

## Design

### Syntax

A `:task` step's value has the same shape as a `:depends` entry: a task symbol, or a vector of the task symbol followed by its args. Each arg is a string (with `{{arg/*}}`/`{{var/*}}` expansion), `:arg/<name>` (forward the caller's bound arg), or `:var/<name>`.

```edn
ci {:args [{:name :env}]
    :do [{:sh "docker compose up -d"}
         {:task fmt}                       ; no args
         {:task [deploy :arg/env "fast"]}  ; with args
         {:sh "docker compose down"}]}
```

### Semantics: "as if the step ran `rite <callee> args`, in-process"

lgx implements `:task` by starting a child `lgx` process, because its built-ins exit the process. rite doesn't need that: it already flattens an invocation into a plan and streams step output live. A `:task` step therefore expands into a **sub-plan** for the called task (its `:depends` graph, then the task itself) and runs that sub-plan in place of the step.

1. **No dedup against the outer plan.** The sub-plan is built with a fresh `:seen` set, the same way a separate `rite <callee>` run would be. `{:depends [fmt] :do [{:task fmt}]}` runs fmt twice, which is what the config says. `:depends` stays the deduped "prerequisites" mechanism, and `:task` is an explicit call. The called task's own `:depends` graph is still deduped *within* its sub-plan.
2. **The called task inherits the caller's `:env` and working directory.** Its effective env is `(merge caller-effective-env own-env)`. Its effective cwd is its own `:cwd` (joined with the project root) if it has one, otherwise the caller's effective cwd (nil means the invocation dir). The called task's `:depends` entries inherit the same way, because they are part of the call. Top-level plan entries inherit nothing, so today's behavior is unchanged. The inherited env is passed down as data and applied around each step's process, not wrapped around the whole `:task` step. That keeps the existing guarantee in `run-steps!`: a task's env never affects `:run` basis resolution or rite's own exe lookup.
3. **Fail fast at plan time.** `build-plan` resolves each `:task` step's args against the caller's bindings and builds the sub-plan before anything runs. A runtime arg error (for example, a forwarded value that fails the callee's enum) comes back as `{:errors}`, the same way `:depends` errors do.
4. **Cycles are caught at load time.** Callees are literal symbols, so `depends-cycle-errors` just adds `:task` callees as edges in its graph. This catches self-calls, `:task` cycles, and mixed `:depends`/`:task` cycles with the existing `dependency cycle: a -> b -> a` message. Because the graph is acyclic, building the plan recursively always terminates. Recursion through `{:sh "rite a"}` is out of scope.
5. **Validation reuses the `:depends` checks.** The shape check is `depends-entry-errors`. The semantic check is `depends-entry-ref-errors`: the callee must exist, placeholders must name a declared arg or defined var, and literal-only args must match the callee's `:args`. It is parameterized with a verb (`"depends on"` / `"calls"`) and a base path. Errors are anchored at `[:tasks <caller> :do <i> :task]`, or `[:tasks <caller> :do :task]` for a single-step-map `:do`. The existing `:arg`/`:var` placeholder check (`step-ref-errors`) skips `:task` steps, since the semantic check covers them.
6. **Output.** The step prints `$ rite <callee> <resolved args...>`, then the sub-plan prints its normal `=> Running task ...` headers and steps. If the called task fails, its own failure line prints first, followed by the caller's `=> Task ci failed: step 3 exited with N`. The exit code propagates unchanged.
7. **No built-in callees.** lgx's `lgx:<name>` form doesn't apply here. rite's only built-ins are `tasks` and `completion`.

### Data shapes (tasks 2 and 3 must agree on these)

A plan entry gains a `:calls` map, keyed by the **0-based** index of the `:task` step in the entry's (normalized, vector) `:do`:

```clojure
{:name 'ci :task {...} :bindings {...}
 :calls {1 {:name 'fmt    :args []               :plan [<entry> ...]}
         2 {:name 'deploy :args ["prod" "fast"]  :plan [<entry> ...]}}}
```

Every entry has `:calls`, and it is `{}` when the task has no `:task` steps. Sub-plan entries have the same shape, including their own `:calls`.

The runtime inheritance context passed down through execution is `{:env {"K" "v"} :cwd <abs-path-or-nil>}`. Top level passes `{:env {} :cwd nil}`.

### Testing

- `test/rite/config_test.lg`: accepts `:task` steps (symbol form, vector form, single-step-map `:do`). Rejects a bad shape, an unknown callee, an undeclared forwarded arg, a literal arg that violates the callee's enum, a self-call cycle, and a mixed `:depends`/`:task` cycle. Existing messages change to list `:sh, :run, :task`.
- `test/rite/plan_test.lg`: `:calls` is built with resolved args and a nested sub-plan (including the callee's `:depends`), there is no dedup against the outer plan, a forwarded enum mismatch inside a call returns `{:errors}`, and entries without `:task` steps have `:calls {}`.
- `tests/e2e.sh` Scenario 12: step order around a call, arg forwarding, failure propagation with both failure lines, env/cwd inheritance, and a load-time cycle error.
