### Part B: color off when stderr is not a terminal

`color-enabled?` today checks only `RITE_NO_COLOR`. The comment claiming let-go has no TTY detection is stale: `term/tty?` exists in 1.12.2 and, verified on this machine, returns `true` for `*err*` under a pty and `false` when stderr is redirected. All status lines go to `*err*`, so stderr is the stream to test.

New rule, any one condition disables color:

- `RITE_NO_COLOR` is non-blank (project override, unchanged).
- `NO_COLOR` is non-blank (the de facto standard, new).
- `(term/tty? *err*)` is false or throws (new; the throw guard covers the `js`/`plan9`/`wasip1` builds where `tty?` is absent).

Structure in `style.lg`:

- `(def ^:dynamic *stderr-tty?* ...)`, a zero-arg fn wrapping `term/tty?` on `*err*` in `try`, returning `false` on any error. Dynamic so tests can `binding` it. (Verified: `^:dynamic` + `binding` work in lg 1.12.2.)
- `(defn color-enabled? [getenv tty?] ...)`, public and pure: takes a getenv fn and a tty predicate, returns a boolean. Same injection style as `script/script-mode?`.
- `colorize` calls `(color-enabled? os/getenv *stderr-tty?*)`.

Testing: `lgx test` captures stderr, so every style test now sees plain output by default. Tests asserting plain shapes bind `*stderr-tty?*` to `(constantly false)`; tests asserting escape codes bind it to `(constantly true)` and blank both env vars. `color-enabled?` gets its own truth-table tests with fake getenv fns. In e2e, Scenario 8 flips its "default is colored" assertion (captured output is now plain) and adds a pty check via util-linux `script`, skipped when unavailable.

Docs: fix the stale comment in `style.lg`, update the `RITE_NO_COLOR` README row, add a `NO_COLOR` row.

### Part C: failure line

When a `:do` step exits non-zero, rite prints nothing. Add one purple line to `*err*`:

```
=> Task fail failed: step 2 exited with 1
```

Step numbers are 1-based, matching how a person counts the `$` lines above it. The line is written from `run-entry!`, where the task name, the step index, and the exit code are all in hand, so `run-entry!` keeps returning the plain exit int and `run-plan!` is untouched. A leading blank line separates it from the failed step's output, the same as step lines.

`style/failure-line [name step-number exit]` is the pure builder, next to `task-header` and `step-line`. Purple, like the other task decoration; the word `failed` carries the signal, and the two-color palette stays as is.

Exit code semantics do not change. `:depends`-only tasks have no steps and never print it.

### Part D: task-level `:env` and `:cwd`

Two optional task keys, applied to every step of that task and to nothing else. They do not propagate to `:depends` entries: a dependency runs with its own `:env`/`:cwd` or none.

**`:env`** is a map of string keys to string or number values.

- Keys: non-blank strings without `=`. `RITE_SCRIPT`, `LG_SOURCE_PATHS`, and `LG_READ_CLJ` are rejected at load with `is managed by rite and cannot be set`.
- Values: string or number (numbers stringified in normalize, like `:vars`). Values accept `{{arg/*}}`/`{{var/*}}` tokens, expanded with `args/expand` against the task's bindings; unknown tokens are load errors, like step strings.
- Mechanism: in `run-entry!`, before the step loop, `os/setenv` each expanded pair, remembering the previous value via `os/getenv`. After the loop (success or failure) restore each. let-go has no `unsetenv`, so a var that was absent is restored to `""`; note this in a comment as `exec-script!` does. Children of `os/exec*` inherit the process env (verified), so both `:sh` and `:run` steps see the vars.
- `--verbose` prints `+ env K=V ...` (keys sorted) once after the task header.

**`:cwd`** is a path relative to the project root, validated by the existing `rel-path-schema`.

- Not `syscall/chdir`: it is `unsupported` on non-Linux builds of let-go (`pkg/rt/syscall_other.go`), and rite ships darwin binaries. Instead, run the step through `sh` with a `cd`, which is what users type by hand today and is portable. The process cwd never changes, so there is nothing to restore and nothing to leak.
  - `:sh` step: the command becomes `cd '<abs cwd>' || exit; <cmd>` (shell-quoted with the existing quoting fn). The `;` terminates the `cd` list, so a `cd` failure exits `sh` with cd's status before any of the user's command runs, and the command keeps its own syntax intact. A `&&` prefix would not do: with `cd x && echo a; echo b`, the `echo b` still runs in the wrong directory and `sh` exits 0 (verified).
  - `:run` step: the child argv becomes `sh -c 'cd "$1" && shift && exec "$@"' sh <abs cwd> <abs exe> <argv...>` (verified working, including a directory with a space). `<abs exe>` is `(first os/args)` made absolute when it is a relative path containing a `/` (such as `./bin/rite` in development), by joining it onto `(os/cwd)` before the `cd`; a bare name without `/` is left for `PATH` lookup. Without this the wrapper fails with `exec: ./bin/rite: not found` (verified).
- `<abs cwd>` is `(path/join project cwd)`, so `rite` invoked from any subdirectory resolves the same directory.
- A missing directory fails inside `sh` (`cd: can't cd to ...`), the step exits non-zero, and the Part C failure line names the step. No extra pre-check.
- `--verbose` already shows the resolved command, which now includes the `cd`.

Schema keys are appended after `:private?` so the closed-map "allowed keys" message only grows at the end.
